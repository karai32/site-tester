# 808 Checker

Сервис проверки сайтов. Сервер — Fastify, страницы собираются на сервере
из шаблонов EJS, база — SQLite, тесты сайта — Playwright. Фронтенд-фреймворка
и сборки нет: файл поправил — перезапустил — работает.

## Запуск

```bash
npm install
npm run add-user -- artem "Артем Тепляков" artem@808group.ru   # покажет пароль
npm run set-password -- artem                                   # новый пароль, если старый забыли
npm run add-project -- Hadassah https://hadassah.moscow/       # создаст проект и полный сценарий
npm run dev                                                     # http://127.0.0.1:3001
npm run check -- 1                                              # проверка по сценарию 1 прямо в терминале
npm run queue-check -- 1                                        # поставить проверку в очередь запущенного сервера
```

`npm run check` нужен для отладки тестов. Не запускайте его, пока работает
сервер: сервер при старте считает идущие проверки прерванными.

Настройки через переменные окружения:

| Переменная | По умолчанию | Что это |
|---|---|---|
| `PORT` | `3001` | Порт сервера |
| `HOST` | `127.0.0.1` | Адрес сервера |
| `DATA_DIR` | `data/` | Папка с базой `app.db` и скриншотами `media/` |
| `NODE_ENV` | — | `production` на сервере: cookie только по https |

## Как идёт проверка

1. Кнопка «Запустить» на дашборде проекта создаёт отчёт со статусом `queued`,
   и он попадает в очередь (`runner/queue.js`).
2. `runner/run-check.js` обходит сайт и сохраняет HTML всех страниц во временную папку.
3. По сценарию выбираются страницы (выборки) и тесты.
4. Тесты запускаются по одному. Результат каждого сразу пишется в базу,
   скриншоты — в `data/media/reports/<id отчёта>/`.
5. Отчёт получает статус `done` (или `error`, если сайт недоступен).

Пока проверка идёт, страница отчёта `/reports/<id>` обновляется сама и показывает
прогресс. Там же её можно отменить: из очереди отчёт убирается сразу, идущая проверка
останавливается после текущего теста. Готовый отчёт скачивается одним HTML-файлом
со встроенными скриншотами.

## Сценарии

Сценарий — набор тестов и выборок страниц. Полный сценарий («Полная проверка»)
создаётся вместе с проектом: все тесты на всех страницах. Остальные создаются
на странице «Сценарии» → «Новый сценарий».

Сценарий не редактируется: «Скопировать и изменить» создаёт новый сценарий-редакцию
с номером в названии («Полный аудит #2»), а старый остаётся — по нему построены
прежние отчёты. Номер можно стереть или заменить своим названием.

**Регулярность** — расписание сценария: каждый день, каждые N часов, раз в N дней,
по будням, по выходным, N числа каждого месяца, ежеквартально. Задаётся при создании
сценария, меняется на его странице без новой редакции. Время — московское.
**Отложенная проверка** — один запуск в выбранные дату и время, её можно отменить.

Время следующего запуска хранится в базе (`next_run_at`, `deferred_at`). Раз в 5 секунд
очередь вызывает `src/runner/scheduler.js`: он ставит в очередь проверки, у которых подошло
время, и считает следующий запуск (`src/schedule.js`). Если прошлая регулярная проверка
сценария ещё идёт, новая пропускается. Выключенный сценарий по расписанию не запускается.

## Уведомления

В сценарии для каждого события из ТЗ выбирается способ — Telegram, почта или «нет» —
и получатели: почты и Telegram ID. События: запуск проверки, итог проверки (ручной
и отложенной) — пройдена или нет по порогу успешности, критические ошибки (проверка не выполнилась),
итог регулярной проверки, повторяющиеся ошибки (тест провален второй раз подряд),
смена статуса теста (по сравнению с прошлым отчётом сценария).

Код — в `src/notifications/`: `settings.js` (настройки и форма), `notify.js` (что отправить
по итогам проверки), `telegram.js` и `email.js` (отправка). Уведомления отправляет
`runner/run-check.js` в начале и в конце проверки. Ошибка отправки пишется в лог и
на проверку не влияет.

Telegram-бот пишет только тем, кто сам ему написал. На любое сообщение бот отвечает
номером чата — это Telegram ID, его указывают в профиле и в сценарии.

**Настройка на сервере** — файл `/etc/808-checker.secrets.env` (в git его нет: там пароли):

```
TELEGRAM_BOT_TOKEN=123456:ABC...     # токен от @BotFather
TELEGRAM_BOT_NAME=checker808_bot     # имя бота без @
SMTP_HOST=smtp.yandex.ru             # почтовый сервер
SMTP_PORT=465
SMTP_USER=checker@808.ru
SMTP_PASS=пароль-приложения
SMTP_FROM="808 Checker <checker@808.ru>"
```

После правки: `chmod 600 /etc/808-checker.secrets.env && systemctl restart 808-checker`.
Без этих настроек сервис работает, а уведомления этим способом не отправляются
(в лог пишется «не настроен»).

## API для других админок

JSON API по адресам `/api/...` — для админки, в которой 808 Checker работает
как микросервис. Справка с примерами всех запросов — в самом сервисе:
**Настройки → Справка по API** (`/settings/api`).

Примеры в справке — настоящие ответы, снятые с тестового сервера командой
`node scripts/api-examples.js http://127.0.0.1:3017 <ключ>` (она создаёт и удаляет данные —
только не на боевом сервере!). Результат — `docs/api-examples.json`, его читает страница справки.
После изменений в API примеры стоит снять заново.

Вход — по API-ключу в заголовке `Authorization: Bearer 808ck_...`. Ключи создаются
и удаляются в «Настройках», запрос выполняется от имени владельца ключа. В базе
(таблица `api_keys`) хранится только sha256 ключа, сам ключ показывается один раз.
Cookie входа в API не действуют.

Код — в `src/api/`: `index.js` (проверка ключа, лимит, ошибки), `response.js`
(формат ответов), `format.js` (записи базы → объекты API), остальные файлы — запросы.
Логику API не дублирует: данные берёт из тех же модулей, что и страницы сервиса
(`dashboard.js`, `scenario-list.js`, `report-list.js`, `report-data.js`, `db/` …) —
поэтому фильтры и цифры в API и в интерфейсе всегда совпадают.

## Как написать тест

Тест — файл в папке своей категории, например `src/tests/seo/title-present.js`:

```js
// Что проверяет тест — одной строкой
export default {
  id: 'title-present',                       // уникальный, не меняется: по нему тест хранится в сценариях
  title: 'Title заполнен на всех страницах', // название в отчёте

  async run({ siteUrl, pages, getHtml, links, browser }) {
    // ... проверка ...
    return { passed: true, comment: 'Проверено 120 страниц' };
  },
};
```

После этого добавьте тест в `src/tests/index.js`.

**Что получает `run`:**

| Поле | Что это |
|---|---|
| `siteUrl` | Адрес сайта проекта: `https://hadassah.moscow/` |
| `pages` | Адреса страниц выборки сценария |
| `getHtml(url)` | HTML страницы из выборки. Уже скачан при обходе, запросов к сайту не делает |
| `links` | Внутренние ссылки на страницах выборки: `[{ url, status, error, foundOn }]` |
| `browser` | Браузер Chromium: `const page = await browser.newPage()` |

**Что возвращает `run`:**

| Поле | Обязательно | Что это |
|---|---|---|
| `passed` | да | `true` — тест пройден, `false` — провален |
| `comment` | да | Комментарий проверки для отчёта |
| `problems` | нет | Список найденных ошибок, по строке на ошибку |
| `pages` | нет | Ссылки на проверенные страницы, если тест проверял конкретные страницы |
| `media` | нет | Скриншоты и видео: `Buffer` или `{ data: Buffer, caption: 'подпись' }` |

Ловить ошибки и закрывать вкладки не нужно: если тест упал, он считается
проваленным с текстом ошибки, а вкладки закрывает раннер. Тест, который идёт
дольше 10 минут, тоже считается проваленным.

Общие функции — в `src/tests/helpers/common.js`: `takeScreenshot(page)`,
`getStatuses(urls)`, `errorMessage(error)`.

## Сервер

Сервис работает на https://audit.808-test.ru (сервер 109.235.116.46, Ubuntu).

| Что | Где |
|---|---|
| Код | `/opt/808-checker` |
| База и скриншоты | `/var/lib/808-checker/data` |
| Браузер для тестов | `/var/lib/808-checker/pw-browsers` |
| Служба | `808-checker` (пользователь `checker`), порт 3001 |
| nginx | `/etc/nginx/sites-available/audit.808-test.ru` → порт 3001 |
| Токены и пароли для уведомлений | `/etc/808-checker.secrets.env` (не в git) |
| Ночная проверка | расписание сценария «Полная проверка»: каждый день в 03:00 по Москве |
| Архив старого сервиса | `/var/backups/site-checker/` — база проверок до переезда |

**Деплой** — автоматически при пуше в `main` (`.github/workflows/deploy.yml`):
код копируется на сервер, ставятся зависимости, файлы из `deploy/` раскладываются
по местам, служба перезапускается. Если в этот момент идёт проверка, деплой
отменяется — запустите его повторно позже (вкладка Actions → Run workflow).

**Команды на сервере** (от root):

```bash
systemctl status 808-checker          # работает ли сервис
journalctl -u 808-checker -f          # логи
# новый пользователь: команды из scripts/ запускаются от пользователя checker с настройками сервиса
cd /opt/808-checker && runuser -u checker -- env $(grep -v '^#' /etc/808-checker.env | xargs) \
  node scripts/add-user.js login "Имя Фамилия" почта
# новый пароль существующему пользователю
cd /opt/808-checker && runuser -u checker -- env $(grep -v '^#' /etc/808-checker.env | xargs) \
  node scripts/set-password.js login
```

## Правила

- **Код — простой.** Лучше две понятные строки, чем одна хитрая: обычные `if` и циклы
  вместо цепочек `.map().filter()`, тернарных операторов в `return` и трюков
  вроде `[...new Set()]`. Код должен читать человек, который не знает JS глубоко.

- **Шаблон только выводит данные.** Всё, что нужно посчитать или отфильтровать,
  делается в маршруте, а в шаблон передаётся готовое.
- **В шаблоне выводим через `<%= %>`** — так текст экранируется, и HTML из
  базы не сломает страницу. `<%- %>` — только для `include` и `body`.
- **SQL пишем руками** в файлах `src/db/*.js`, по одному файлу на таблицу.
- **Изменить базу** — добавить файл в `src/db/migrations/` со следующим номером.
  Старые миграции не меняем: они уже выполнены на сервере.
- **Внешний вид** — по макету Figma. Каждый элемент собираем из UI-кита 808 Utilities:
  тот же элемент → похожий → аналог по смыслу, и только если в ките ничего нет — свой.
- **Цвета** — только переменные из `public/assets/css/theme.css`.
  Свои стили — в `public/assets/css/app.css`.
- **Разметка компонентов** берётся из UI-кита (`/ui.html`).
