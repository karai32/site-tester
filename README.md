# 808 Checker

Сервис, который проверяет сайты. Сервер написан на Fastify, страницы собираются
на сервере из шаблонов EJS, данные хранятся в SQLite, тесты сайтов работают через
Playwright. Фронтенд-фреймворка и сборки нет: поправил файл, перезапустил, работает.

## Запуск у себя

```bash
npm install
npm run add-user -- artem "Артем Тепляков" artem@808group.ru   # создать пользователя, покажет пароль
npm run set-password -- artem                                   # выдать новый пароль
npm run add-project -- Hadassah https://hadassah.moscow/       # создать проект и его полную проверку
npm run dev                                                     # сайт на http://127.0.0.1:3001
npm run check -- 1                                              # проверка по сценарию 1 прямо в терминале
npm run queue-check -- 1                                        # поставить проверку в очередь работающего сервера
```

`npm run check` нужен, чтобы отлаживать тесты. Не запускайте его, пока работает
сервер: при старте сервер считает все идущие проверки прерванными.

Можно запустить и в Docker, так же, как на сервере:

```bash
docker compose up -d --build    # собрать образ и запустить, сайт на http://localhost:3002
docker compose exec checker node scripts/add-user.js test "Тест"
docker compose down             # остановить
```

В Docker база лежит в папке `docker-data/`, отдельно от `data/`.

Настройки задаются переменными окружения:

| Переменная | По умолчанию | Что это |
|---|---|---|
| `PORT` | `3001` | порт сервера |
| `HOST` | `127.0.0.1` | на каком адресе сервер принимает запросы |
| `DATA_DIR` | `data/` | папка с базой `app.db` и скриншотами `media/` |
| `NODE_ENV` | не задана | на сервере `production`, тогда cookie входа работают только по https |
| `APP_URL` | `http://localhost:3001` | адрес сайта для ссылок в уведомлениях |

## Как идёт проверка

1. Кнопка «Запустить» на дашборде создаёт отчёт со статусом `queued`, и он встаёт
   в очередь (`runner/queue.js`).
2. `runner/run-check.js` обходит сайт и сохраняет HTML всех страниц во временную папку.
3. По сценарию выбираются нужные страницы и тесты.
4. Тесты запускаются по одному. Результат каждого сразу пишется в базу, скриншоты
   сохраняются в `data/media/reports/<номер отчёта>/`.
5. Отчёт получает статус `done`. Если сайт недоступен, статус будет `error`.

Пока проверка идёт, страница отчёта `/reports/<номер>` сама обновляется и показывает,
сколько тестов уже прошло. Там же проверку можно отменить: если она ещё в очереди, она
сразу убирается, а если уже идёт, то остановится после текущего теста. Готовый отчёт
можно скачать одним HTML-файлом, скриншоты будут внутри.

## Сценарии

Сценарий это набор тестов и выборок страниц. Вместе с проектом создаётся сценарий
«Полная проверка»: все тесты на всех страницах. Остальные создаются на странице
«Сценарии», кнопка «Новый сценарий».

Сценарий нельзя отредактировать. Кнопка «Скопировать и изменить» создаёт новый
сценарий с номером редакции в названии, например «Полный аудит #2», а старый остаётся,
потому что по нему построены прежние отчёты. Номер в названии можно стереть или
заменить своим текстом.

**Регулярность** это расписание сценария: каждый день, каждые N часов, раз в N дней,
по будням, по выходным, N-го числа каждого месяца, раз в квартал. Её задают при создании
сценария и меняют на его странице, новая редакция при этом не создаётся. Время московское.

**Отложенная проверка** запускается один раз в выбранные дату и время. Её можно отменить.

Время следующего запуска хранится в базе, в полях `next_run_at` и `deferred_at`.
Каждые 5 секунд очередь вызывает `src/runner/scheduler.js`. Он ставит в очередь
проверки, у которых подошло время, и считает следующий запуск (`src/schedule.js`).
Если прошлая регулярная проверка этого сценария ещё не закончилась, новая пропускается.
Выключенный сценарий по расписанию не запускается.

## Уведомления

В сценарии для каждого события выбирается, куда писать: в Telegram, на почту или
никуда. Там же указываются получатели: адреса почты и Telegram ID.

События:
- проверка началась;
- проверка закончилась (ручная или отложенная), пройдена она или нет по порогу успешности;
- критическая ошибка, то есть проверка не выполнилась;
- закончилась регулярная проверка;
- повторяющаяся ошибка, тест провален второй раз подряд;
- у теста сменился статус по сравнению с прошлым отчётом этого сценария.

Код лежит в `src/notifications/`:
- `settings.js` настройки и форма;
- `notify.js` решает, что отправить по итогам проверки;
- `telegram.js` и `email.js` отправляют.

Уведомления отправляет `runner/run-check.js` в начале и в конце проверки. Если отправить
не получилось, это пишется в лог, а на саму проверку никак не влияет.

Telegram-бот может писать только тем, кто сам ему написал. На любое сообщение бот
отвечает номером чата. Это и есть Telegram ID, его вписывают в профиль и в сценарий.

**Настройка на сервере.** Токен бота и пароль от почты лежат в файле
`/etc/808-checker.secrets.env`. В git его нет, потому что там пароли.

```
TELEGRAM_BOT_TOKEN=123456:ABC...     # токен от @BotFather
TELEGRAM_BOT_NAME=checker808_bot     # имя бота без @
SMTP_HOST=smtp.yandex.ru             # почтовый сервер
SMTP_PORT=465
SMTP_USER=checker@808.ru
SMTP_PASS=пароль-приложения
SMTP_FROM="808 Checker <checker@808.ru>"
```

После изменения файла перезапустите контейнер, чтобы он прочитал новые настройки:

```bash
chmod 600 /etc/808-checker.secrets.env
cd /opt/808-checker-docker && docker compose up -d --force-recreate
```

Без этих настроек сервис работает как обычно, просто уведомления этим способом
не уходят, а в логе появляется запись «не настроен».

## API для других админок

По адресам `/api/...` работает JSON API. Через него 808 Checker подключается
к другой админке как микросервис. Справка с примерами всех запросов есть в самом
сервисе: «Настройки», кнопка «Справка по API» (`/settings/api`).

Примеры в справке это настоящие ответы, снятые с тестового сервера командой
`node scripts/api-examples.js http://127.0.0.1:3017 <ключ>`. Эта команда создаёт
и удаляет данные, поэтому на боевом сервере её запускать нельзя. Ответы сохраняются
в `src/api/examples.json`, оттуда их берёт страница справки. Если API поменялось,
примеры нужно снять заново.

Вход по API-ключу в заголовке `Authorization: Bearer 808ck_...`. Ключи создаются
и удаляются в «Настройках». Запрос выполняется от имени того, кто создал ключ.
В базе (таблица `api_keys`) хранится только хеш ключа, а сам ключ показывается один раз.
Cookie входа для API не работают.

Код лежит в `src/api/`:
- `index.js` проверяет ключ и оформляет ошибки;
- `response.js` задаёт формат ответов;
- `format.js` превращает записи из базы в объекты API;
- остальные файлы это сами запросы.

Свою логику API не дублирует. Данные берутся из тех же модулей, что и для страниц
сервиса (`dashboard.js`, `scenario-list.js`, `report-list.js`, `report-data.js`, `db/`),
поэтому фильтры и цифры в API и в интерфейсе всегда совпадают.

## Как написать тест

Тест это файл в папке своей категории, например `src/tests/seo/title-present.js`:

```js
// Что проверяет тест, одной строкой
export default {
  id: 'title-present',                       // уникальный и не меняется: по нему тест хранится в сценариях
  title: 'Title заполнен на всех страницах', // название в отчёте

  async run({ siteUrl, pages, getHtml, links, browser }) {
    // ... проверка ...
    return { passed: true, comment: 'Проверено 120 страниц' };
  },
};
```

Потом добавьте тест в `src/tests/index.js`.

**Что получает `run`:**

| Поле | Что это |
|---|---|
| `siteUrl` | адрес сайта проекта, например `https://hadassah.moscow/` |
| `pages` | адреса страниц из выборки сценария |
| `getHtml(url)` | HTML страницы из выборки. Он уже скачан при обходе, к сайту запрос не идёт |
| `links` | внутренние ссылки на страницах выборки: `[{ url, status, error, foundOn }]` |
| `browser` | браузер Chromium: `const page = await browser.newPage()` |

**Что возвращает `run`:**

| Поле | Обязательно | Что это |
|---|---|---|
| `passed` | да | `true`, если тест пройден, и `false`, если провален |
| `comment` | да | комментарий для отчёта |
| `problems` | нет | найденные ошибки, по строке на каждую |
| `pages` | нет | ссылки на страницы, которые тест проверял |
| `media` | нет | скриншоты и видео: `Buffer` или `{ data: Buffer, caption: 'подпись' }` |

Ловить ошибки и закрывать вкладки в тесте не нужно. Если тест упал, он считается
проваленным, а текст ошибки попадает в отчёт. Вкладки закрывает раннер. Тест, который
идёт дольше 10 минут, тоже считается проваленным.

Общие функции для тестов лежат в `src/tests/helpers/common.js`: `takeScreenshot(page)`,
`getStatuses(urls)`, `errorMessage(error)`.

## Сервер

Сервис работает на https://audit.808-test.ru в Docker.

| Что | Где |
|---|---|
| Сервер | 109.235.116.46, Ubuntu |
| Файл запуска | `/opt/808-checker-docker/docker-compose.yml`, это копия `deploy/docker-compose.yml` |
| Контейнер | `808-checker`, слушает порт 3001 только внутри сервера |
| База и скриншоты | `/var/lib/808-checker/data`, подключена к контейнеру как папка `/app/data` |
| Пароли для уведомлений | `/etc/808-checker.secrets.env`, в git его нет |
| nginx | `/etc/nginx/sites-available/audit.808-test.ru`, передаёт запросы в контейнер. Копия настроек лежит в `deploy/nginx.conf` |
| Образы сервиса | `ghcr.io/karai32/site-tester` |
| Ночная проверка | расписание сценария «Полная проверка», каждый день в 03:00 по Москве |
| Архив старого сервиса | `/var/backups/site-checker/`, база проверок до переезда |

Node.js и браузер на сервер не ставятся: всё нужное уже внутри образа.

**Выкладка** запускается сама после каждого пуша в `main` (`.github/workflows/deploy.yml`):
1. GitHub собирает образ по `Dockerfile` и кладёт его в реестр ghcr.io с двумя именами:
   `latest` и хеш коммита.
2. Если на сервере сейчас идёт проверка, выкладка останавливается, чтобы её не оборвать.
   Тогда запустите выкладку позже вручную: вкладка Actions, кнопка Run workflow.
3. На сервер копируется `deploy/docker-compose.yml`, сервер скачивает новый образ
   и перезапускает контейнер. Старые образы удаляются, чтобы не занимать место.
4. Выкладка ждёт, пока сервис ответит на `/health`. Если он не поднялся, в логе
   выкладки будут последние строки логов контейнера.

Сам файл `docker-compose.yml` на сервере руками не меняют: при следующей выкладке
он всё равно перезапишется копией из git.

**Команды на сервере** (от root):

```bash
cd /opt/808-checker-docker
docker compose ps                    # работает ли контейнер
docker compose logs -f               # логи, выход по Ctrl+C
docker compose restart               # перезапустить сервис
docker compose exec checker node scripts/add-user.js login "Имя Фамилия" почта   # новый пользователь
docker compose exec checker node scripts/set-password.js login                    # новый пароль
```

**Вернуть прошлую версию.** В `/opt/808-checker-docker/docker-compose.yml` замените
`latest` на хеш нужного коммита (его видно на GitHub в списке коммитов) и выполните
`docker compose up -d`. Следующая выкладка снова поставит `latest`.

## Правила

- **Код пишем просто.** Лучше две понятные строки, чем одна хитрая. Обычные `if` и циклы
  вместо цепочек `.map().filter()`, тернарных операторов в `return` и трюков вроде
  `[...new Set()]`. Код должен понимать человек, который знает JS не очень глубоко.
- **Шаблон только выводит данные.** Всё, что нужно посчитать или отфильтровать,
  делается в маршруте, а в шаблон передаётся уже готовое.
- **В шаблоне выводим через `<%= %>`.** Так текст экранируется, и HTML из базы не сломает
  страницу. `<%- %>` нужен только для `include` и `body`.
- **SQL пишем руками** в файлах `src/db/*.js`, по одному файлу на таблицу.
- **Чтобы изменить базу,** добавьте файл в `src/db/migrations/` со следующим номером.
  Старые миграции не трогаем, они уже выполнены на сервере.
- **Внешний вид берём из макета Figma.** Каждый элемент собираем из UI-кита 808 Utilities:
  сначала ищем такой же элемент, потом похожий, потом подходящий по смыслу, и только если
  в ките ничего нет, верстаем свой.
- **Цвета** берём только из переменных в `public/assets/css/theme.css`.
  Свои стили пишем в `public/assets/css/app.css`.
- **Разметку компонентов** берём из UI-кита (`/ui.html`).
- **В текстах без длинных тире**, стрелок и лишних пояснений.
